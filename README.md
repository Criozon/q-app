# Q-App — приложение для электронных очередей

Создание электронной очереди за несколько секунд: организатор задаёт название,
количество окон и список услуг, получает QR-код и ссылку, участники сканируют
код и встают в очередь, операторы вызывают их из панели своего окна.

**Продакшен:** https://q-app-queue.vercel.app

## Стек

- TypeScript в строгом режиме; типы таблиц и функций генерируются из схемы:
  `supabase gen types typescript --project-id <ref> > src/types/database.ts`
- React 19 + Vite 7 (`@vitejs/plugin-react`)
- react-router-dom 7 (`BrowserRouter`, поэтому на хостинге нужен SPA-fallback — см. `vercel.json`)
- Хостинг: Vercel, проект `q-app-queue`. Переменные окружения заводятся
  с `--type config`: CLI иначе отказывается принимать `VITE_`-переменную,
  похожую на ключ. Для anon-ключа Supabase это правильно — он публичный
  по устройству и всё равно уезжает в бандл, защита на стороне RLS.
- Supabase: PostgreSQL + PostgREST + Realtime. Аутентификации нет, весь доступ под ролью `anon`
- lucide-react (иконки), react-hot-toast (уведомления), qrcode (генерация QR)

## Быстрый старт

```bash
npm install
cp .env.example .env    # и подставить URL + anon-ключ своего проекта Supabase
npm run dev
```

Переменные окружения (читаются в `src/services/supabaseService.js`):

| Переменная | Назначение |
| --- | --- |
| `VITE_SUPABASE_URL` | URL проекта Supabase |
| `VITE_SUPABASE_ANON_KEY` | Публичный anon-ключ проекта |

Без них приложение падает на старте с `supabaseUrl is required`.

**Обязательная настройка проекта Supabase:** в панели включить
Authentication → Sign In / Providers → **Allow anonymous sign-ins**.
Без этого приложение не получит сессию, а политики доступа не отдадут
ничего — экран останется пустым без внятной ошибки.

Скрипты: `npm run dev` · `npm run build` · `npm run preview` · `npm run lint` · `npm run typecheck` · `npm test`

`npm run build` проверяет типы перед сборкой, так что сломанные типы до продакшена не доедут.

## База данных

Схема лежит в [`supabase/migrations/0001_init.sql`](supabase/migrations/0001_init.sql).
Тела RPC-функций перенесены из бэкапа исходного проекта Supabase — это рабочая
логика, а не реконструкция по клиентскому коду.

**Как применять миграции.** Через `supabase db push` (нужен пароль базы) либо
копипастом в SQL Editor. Во втором случае есть подвох: вставка в редактор
портит не-ASCII символы — `'Окно '` превращается в `'–Ю–Ї–љ–Њ '`. Комментарии
от этого только теряют читаемость, а вот строковые литералы внутри функций
ломаются по-настоящему. Если применяете через браузер, загоняйте SQL в base64
и раскодируйте уже на странице, либо потом проверьте литералы запросом
`select prosrc from pg_proc where proname = 'create_queue_with_services_and_windows'`.

Таблицы: `queues`, `services`, `windows`, `window_services` (связка «окно ↔ услуга»),
`queue_members`. Плюс RPC-функции — вся нетривиальная логика (создание очереди
со всеми окнами и услугами, вызов следующего участника с учётом услуг окна,
загрузка панели окна одним запросом) живёт в базе, не на клиенте.

Клиент подписывается на Realtime-события таблиц `queues`, `queue_members`,
`services`, `window_services`, поэтому они должны быть в публикации
`supabase_realtime`, а `queues` и `queue_members` — с `replica identity full`
(код читает `payload.old.id` при удалении очереди). Миграция это настраивает.

## Маршруты и роли

| Маршрут | Кто | Что делает |
| --- | --- | --- |
| `/` | организатор | создание очереди; список своих очередей хранится в `localStorage` |
| `/admin/:secretKey` | администратор очереди | общая панель: участники, окна, услуги, пауза записи, QR |
| `/window-admin/:shortKey` | оператор окна | вызов следующего / конкретного участника, завершение обслуживания |
| `/join/:shortId` | участник | выбор услуги, ввод имени, вход в очередь |
| `/wait/:queueId/:memberId` | участник | статус, номер, «Я иду» / «Отказаться» |
| `/print/:queueId` | организатор | версия для печати |

## Выдача под таймер

Не всякое обслуживание заканчивается у стойки. Прокат лодок, солярий,
картинг, аренда дорожки: человек уходит с чем-то на время, а место
занято, пока он не вернётся. Для таких случаев у участника есть два
поля — свободная заметка (`note`) и момент окончания (`timer_ends_at`) —
и отдельный статус `in_service`.

Ключевое отличие от `called`: вызванный у окна всегда один, а принятых
под таймер может быть сколько угодно. Лодочник выдал пять катамаранов —
видит пять карточек с отсчётом, просроченные наверху и красным.

Чего здесь сознательно нет: учёта самих единиц. Ни «какая лодка
свободна», ни «кабина дезинфицируется», ни «катамаран сломан».
Администратор видит свои лодки глазами, и приложение здесь помощник,
а не система учёта. Заметка — просто текст, а когда закончить, решает
человек, а не программа.

Время считает сервер (`start_member_session`, `extend_member_timer`):
иначе убежавшие часы на устройстве администратора сдвинули бы таймеры
сразу у всех участников. Ответы запросов несут `server_now`, по нему
клиент один раз вычисляет поправку и дальше ведёт отсчёт своими
силами — в том числе без связи, см. `src/utils/clock.ts`.

Длительность набирается двумя циферблатами — часы и минуты, как на
телефоне. Стрелки держат нажатие: одиночное касание — шаг, удержание —
разгон, иначе сорок минут набирались бы сорока нажатиями. По числу
можно ударить и ввести значение с клавиатуры. Готовых пресетов нет
намеренно: солярий продаёт минуты, лодку берут на десятки минут, место
в кемпинге — на часы, и один набор на все три случая не подобрать.

Шаг стрелки считается функциональным обновлением, а не от значения,
замкнутого в обработчике. Иначе интервал удержания навсегда прибавляет
к тому числу, которое было в момент нажатия — ровно та же ловушка, на
которой уже обожглись с таймером опроса на странице ожидания.

Продление — это тот же таймер, взведённый заново: минуты добавляются
к концу, а если время уже вышло — отсчитываются от текущего момента.

Завершение приёма гасит таймер (`0008`). Иначе закрытый досрочно
участник уходил в зачёркнутые, а отсчёт продолжал идти и через минуту
показывал просрочку — прямая ложь: лодку вернули раньше срока.
Заметка при этом остаётся: она говорит, что человеку выдавали.

Заметку и таймер меняет только персонал очереди. Политика доступа
разрешает участнику править свою строку целиком, поэтому ограничение
стоит триггером (`0005_guard_session_fields.sql`) — иначе клиент мог бы
отодвинуть себе оплаченное время сам.

## Управление — на карточках

Вызвать, вернуть, завершить, удалить, задать время и написать заметку
можно у любого участника, прямо на его карточке. Раньше эти действия
жили в подвале и относились к «текущему вызванному» — то есть работать
можно было только по одному и строго по порядку. Прокату это не
годится: по очереди может идти лодка, а освободиться катамаран, и
позвать нужно того, кто дальше в списке.

По той же причине снят запрет вызывать второго, пока первый вызван.

В подвале осталась одна кнопка — «Вызвать следующего». Она не дубль
карточной: зовёт через `call_next_member_to_window`, который учитывает
привязку услуг к окнам, тогда как кнопка на карточке вызывает
конкретного человека в обход маршрутизации. Завершение приёма при этом
никого не вызывает автоматически — это отдельное решение и отдельное
нажатие.

Карточка — одна горизонтальная строка: слева сведения, справа отметки
и кнопки. Отметки (заметка и таймер) отделены от кнопок управления
зазором шире внутренних: первые про содержание выдачи, вторые про ход
очереди.

Главное действие подписано словом: «Вызвать» у ожидающего, «Закончить»
у остальных. Вызов зелёный — как у светофора, «можно идти»; тем же
зелёным мигает фон у клиента, когда его вызывают, так что цвет
читается одинаково с обеих сторон. Завершение — действие обыденное,
ему синий. Значками они были неразличимы — зелёная галочка и красный
человечек рядом читались как две стороны одного «закончить».

Возврат в очередь и удаление нужны редко и рядом с главным действием
только путали, поэтому уехали в меню под тремя точками. Меню выпадает
поверх списка, а не раздвигает карточку: иначе соседние строки уезжают
из-под взгляда ровно в момент выбора.

Там же живёт «Сделать заметку». Значка она не получила намеренно:
речевой пузырёк в этом ряду читается как «написать клиенту» — тем
более что Telegram-бот в планах, — а любая другая иконка требует
догадки. Подписью же в строку сведений она не влезала и вытесняла
состояние. В меню подпись помещается целиком. Когда заметка уже есть,
её правят быстрее — нажатием на строку сведений, где она и написана.

Таймер спрятан за значком, пока его не завели: очереди без выдачи он
не нужен, а места в строке немного. Как только время пошло, значок
сменяется отсчётом.

И заметка, и таймер открываются модальным окном, а не раскрытием
карточки: иначе список разъезжается под пальцем и соседние строки
уезжают из-под взгляда.

Заметку писал человек, а не программа, поэтому в строке сведений она
заметно крупнее остального и своего тона — серого, но темнее
служебного текста. Цветной делать не стали: она перетянула бы внимание
с таймера и кнопок, а размера и веса хватает, чтобы читаться первой.

Заметка стоит в одной строке со сведениями, а не отдельным блоком.
Строка не переносится: не влезло — уходит в фейд (так видно, что текст
продолжается, а не обрывается рубленым краем), полностью видно во
всплывающей подсказке, а на телефоне по нажатию, которое открывает ту
же заметку на правку. Нажатие ловит вся строка: у
подрезанной заметки не осталось бы цели под палец.

Список отсортирован по тому, что требует внимания: сначала те, у кого
идёт время (просроченные первыми), затем вызванные, затем ожидающие
(см. `src/utils/memberOrder.ts`).

## Что видно на входе

Сканируя QR-код, человек видит не только название очереди и услуги,
но и сколько людей уже ждёт и сколько примерно длится приём: именно
это решает, вставать сейчас или зайти позже.

Среднее время показывается, только когда его есть из чего считать.
Прогноз ожидания при отсутствии данных подставляет 4 минуты — без этого
первым участникам нечего показать, — но на экране входа такая четвёрка
выглядела бы измеренной величиной. Поэтому измеренное и подставленное
разведены (`measured_service_minutes` против `avg_service_minutes`,
миграция 0010), и оба случая закреплены тестами.

Примечание очереди, которое пишут при её создании, теперь правится
в настройках: раньше поправить его было негде.

## Модель доступа

Права в приложении двух разных природ, поэтому и механизма два.

**Личность.** Каждый посетитель при первом заходе получает анонимный JWT
(Supabase Anonymous Sign-In) со стабильным `auth.uid()`. Для пользователя
это невидимо — ни регистрации, ни единого лишнего действия. На этом
держится владение талоном: участник видит и меняет только свою строку.

**Ключ-пропуск.** Права администратора очереди и оператора окна держатся
на знании ссылки, и ссылку можно переслать коллеге на другое устройство.
Поэтому ключ обменивается на запись в `queue_access`, привязанную к
`auth.uid()`: `claim_queue_admin(secret)` и `claim_window_operator(short_key)`.
Ссылка работает у всех, кому её дали, но прямой доступ к таблицам есть
только у тех, кто ключ предъявил.

После обмена RLS пускает персонал к таблицам напрямую — это обязательно,
потому что Realtime подчиняется тем же политикам: без доступа на чтение
события просто не придут.

Следствие для страницы ожидания: участник больше не видит чужие строки,
поэтому подписка сужена до собственной, а «перед вами N человек» и прогноз
времени приходят функцией `get_my_queue_status` (плюс опрос раз в 15 секунд —
чужие изменения иначе до него не доходят).

## Тесты

`npm test` — проверки слоя доступа и логики в БД (встроенный тест-раннер
Node, без дополнительных зависимостей): `tests/api.test.mjs` — политики
и логика, `tests/realtime.test.mjs` — доставка событий участнику,
`tests/sessions.test.mjs` — выдача под таймер.

Гоняются против настоящего проекта Supabase из `.env`: локального стека нет,
Docker не ставили сознательно — проект некоммерческий. Каждый прогон
создаёт свою очередь и удаляет её в конце, так что тесты не мешают друг
другу и не оставляют мусора.

**Про лимит auth.** Тестам нужно около двух десятков анонимных личностей,
а лимит запросов к `/auth/v1` у Supabase общий и на бесплатном тарифе
выбирается за пару прогонов — причём падало это в чужих местах, где про
лимит не подумаешь. Поэтому личности заводятся один раз и складываются
в `tests/.auth-cache-*.json` вместе с токенами и сроком их годности:
пока токен жив (около часа), прогон в auth не ходит вовсе.

Если кэш пуст или протух и прогон упёрся в 429 — `npm run test:auth`
заполнит его, пережидая лимит. Кэш не коммитится и его можно удалять.

Покрыто то, что ломается тихо и дорого: изоляция данных между
пользователями, работа секретной ссылки на другом устройстве, нумерация
талонов внутри очереди, маршрутизация вызова по услугам окна,
ограничение на откладывание, права на объявления и итоги, блокировка
записи в приостановленную очередь.

## Сессия живёт час — и обновляется

Токен анонимного входа действует 60 минут, а вкладку держат открытой
дольше. Обновляет его supabase-js сам, но `ensureSession()` запоминал
результат навсегда и больше не смотрел на срок: стоило фоновому
обновлению сорваться — и приложение до перезагрузки слало запросы
с мёртвым JWT, получая на каждое действие 401 `PGRST301`. Со стороны
это выглядело как «иногда не удаётся вызвать участника», а лечилось
закрытием и открытием вкладки.

Теперь кэш проверяется на срок (с запасом в две минуты), а на ответ
401 запрос повторяется один раз со свежей сессией — приложение чинится
само. Обновление общее на все параллельные запросы: у auth свой лимит,
и пять одновременных обновлений сделали бы хуже, чем было.

Новый анонимный вход вместо обновления не делается намеренно: это был
бы другой `auth.uid()`, то есть потеря доступа к своему талону или
к своей очереди.

Код `PGRST301` и конечность срока токена закреплены тестами: если
Supabase их сменит, самопочинка молча перестанет работать.

## Возврат опоздавшего

«Закончить» жмут не только по факту обслуживания. Если человек не
услышал вызова и не подошёл, его так же закрывают — иначе он держит
очередь. Объявился через полчаса — раньше вернуть его было нечем:
`canReturn` исключал именно закончённых, и оставалось просить встать
заново, с новым талоном в хвосте.

Теперь «Вернуть в очередь» есть и у них. Приоритет получается сам
собой, без отдельного механизма: внутри ожидающих порядок по номеру
талона, а у опоздавшего он меньше, чем у всех, кто записался после.
Возвращается — встаёт впереди них.

Следы прошлого захода стирает триггер `tg_track_status_timestamps`:
время вызова, время окончания, пометку и таймер. Иначе человек вернулся
бы в список ожидания с чужим катамараном в карточке.

Чего это не покрывает: удалённых. `deleteMember` и `leaveQueue` сносят
строку насовсем, возвращать нечего.

## Сон устройства

Телефон с погашенным экраном морозит вкладку целиком: интервалы не
тикают, сокет реального времени висит или молча оборван, а браузер об
этом не сообщает. Страница, вернувшись к человеку, показывала то же,
что час назад, — пока не подойдёт очередной опрос. На телефоне это
и выглядит как «вызов не пришёл»: он пришёл, просто никто не слушал
и никто не переспросил.

`useWakeRefresh` ловит возвращение вкладки (снова видна, вернулась из
bfcache, вернулась сеть) и сразу переспрашивает сервер. Если вкладка
была вне поля зрения дольше тридцати секунд или сокет сам видит обрыв,
подписки пересобираются.

Пересобирать приходится именно пересозданием каналов. Соблазнительное
`realtime.disconnect()` внутри делает `teardown()`, но НЕ переводит
каналы в `closed`, а `channel.subscribe()` работает только из `closed`:
после такой «пересборки» страница осталась бы с живым сокетом и без
единой подписки. Тихо и навсегда.

Хук стоит и на странице ожидания, и в обоих провайдерах админки:
планшет у окна засыпает так же, как телефон в кармане.

Чего это не чинит: пока экран погашен, страница заморожена и показать
уведомление не может. Настоящее решение — Web Push с VAPID-ключами
и серверной частью, которая шлёт уведомление при вызове. Отдельная
задача; сейчас `sw.js` умеет только показать уведомление по просьбе
живой страницы.

## Замок сессии

supabase-js сериализует работу с сессией через `navigator.locks` и ждёт
замок **бесконечно** — во всех вызовах `acquireTimeout = -1`. Замок при
этом берётся на каждый запрос к данным: PostgREST спрашивает текущий
токен. Значит, пока замок держит кто-то другой, встаёт всё приложение.

Держит его, например, вкладка с погашенным экраном: система заморозила
её посреди обновления токена, отпустить замок некому. Человек будит
телефон, жмёт «Я иду!» — и двадцать секунд смотрит на «Подтверждаем…»,
после чего получает «не удалось».

Проверено опытом: под удержанным замком действие висит ровно столько,
сколько замок держат. После починки то же действие проходит за пять
секунд ожидания плюс сам запрос — при всё ещё удерживаемом замке.

`makeBoundedLock` ждёт замок пять секунд, дальше работает без него.
Худшее последствие — две вкладки обновят токен одновременно; Supabase
держит прежний refresh-токен годным ещё некоторое время. Замереть на
двадцать секунд и соврать «не удалось» — хуже.

## Журнал сбоев

Сбои случаются на телефоне, где консоли нет, и от них оставалось одно
«Не удалось вызвать участника» без причины: пойманные ошибки глотались
пустым `catch`. Теперь каждая пишется в журнал с источником и причиной,
а тост показывает причину человеку.

Журнал — кольцевой буфер на 200 записей в памяти вкладки
(`src/utils/logger.ts`). На диск не пишется намеренно: в записях мелькают
имена участников, и хранить их дольше сессии незачем. В консоль по-прежнему
льётся только в разработке.

Посмотреть и скопировать — в настройках очереди, блок «Журнал сбоев».
С компьютера доступен как `qappLog()` в консоли.

## Устойчивость

Два правила, оплаченные реальными поломками:

**Ни один сетевой вызов не ждёт вечно.** Все запросы идут через
`withSession` с таймаутом (`src/utils/timeout.ts`). Дело не только в
медленной сети: supabase-js берёт блокировку через `navigator.locks` и,
если таймаут не задан, ждёт её без ограничения — при нескольких открытых
вкладках приложения одна может застрять навсегда. Снаружи это выглядит
как вечный спиннер «Создаём очередь…».

**Первая загрузка повторяется при сбое.** Страницы администратора и окна
загружаются через `withRetry` (`src/utils/retry.ts`): три попытки с
нарастающей паузой. Раньше загрузка была ровно одна — одна заминка в сети
оставляла человека на экране ошибки до перезагрузки вручную. На экране
ошибки есть кнопка «Попробовать снова».

**Сетевой сбой и «объекта нет» — разные сообщения.** Раньше при обрыве
связи админка писала «Очередь не найдена, возможно она была удалена», и
организатор решал, что потерял очередь. Теперь причина определяется
(`errorKind`) и текст подбирается под неё.

**Ни одна ошибка не должна белить экран.** В корне приложения стоит
`ErrorBoundary`. Отдельно обезврежен показ уведомлений: Chrome на Android
запрещает `new Notification()` и бросает исключение, а исключение внутри
`useEffect` заставляет React снести всё дерево. Уведомления показываются
через `src/utils/notifications.ts` — сначала service worker (единственный
рабочий путь на Android), потом конструктор, и всё под `try/catch`.

Включая загрузку (`setIsProcessing(true)`), всегда закрывайте её в
`finally`: сервисный слой при ошибке бросает, и без `finally` кнопки
остаются заблокированными до перезагрузки страницы.

## Известные ограничения

- **Прогноз времени — оценка, а не обещание.** Считается как
  «людей впереди ÷ окон × средняя длительность приёма» по последним
  20 обслуженным. Пока статистики нет, берётся 4 минуты — иначе первым
  участникам нечего показать. В итогах организатора такой подстановки нет:
  там пустое значение показывается прочерком, чтобы не выдавать
  выдуманное число за измеренное.
- **Предупреждение о конце времени срабатывает, только пока страница жива.**
  Сам отсчёт идёт и без связи — момент окончания известен заранее, — но
  запланировать уведомление на будущий момент веб не умеет: API, который
  это делал (Notification Triggers), дальше эксперимента в Chrome не ушёл,
  а обычный таймер замораживается, когда вкладка уходит в фон. Экран ради
  этого намеренно не удерживается: человек уходит на сорок минут, и всё
  это время гореть экраном — просто посадить батарею. Надёжная половина
  здесь — предупреждение администратору: он стоит у стойки и видит
  просрочку красным.
- **Уведомления на iOS.** `new Notification()` в Safari на iPhone не работает
  вне установленного на домашний экран PWA, а при заблокированном экране
  страница выгружается вместе с Realtime-соединением. Нужен Web Push через
  Service Worker. Подробнее — в разделе ниже.
- **Сортировка окон.** `getWindowsByQueueId` сортирует по `name` как по тексту,
  поэтому при 10+ окнах порядок будет «Окно 1, Окно 10, Окно 2».
- **Форма полей `service_name` / `window_name` различается** между источниками:
  из PostgREST-embed (`getMembersByQueueId`) приходят объекты `{ name }`,
  из RPC `get_window_admin_initial_data` — плоские строки. Страницы рассчитаны
  каждая на свой вариант, менять форму в одном месте нельзя. Обе формы описаны
  в `src/types/domain.ts`, так что перепутать их теперь не получится молча.

## Уведомления при заблокированном экране (iOS)

Текущая схема — `new Notification()` + зацикленный `<audio>` на странице
ожидания — на iPhone не срабатывает принципиально:

1. В обычной вкладке Safari на iOS объекта `Notification` вообще нет.
2. Уведомления доступны только установленному на домашний экран PWA (iOS 16.4+)
   и только через `ServiceWorkerRegistration.showNotification()`.
3. При блокировке экрана iOS выгружает страницу: WebSocket Realtime рвётся,
   таймеры останавливаются, звук не играет. Событие «вас вызвали» до страницы
   просто не доходит.

Рабочее решение — Web Push: manifest + Service Worker, подписка `PushManager`
с VAPID-ключами, хранение подписок в базе и Supabase Edge Function, которая
шлёт push при переводе участника в статус `called`.
